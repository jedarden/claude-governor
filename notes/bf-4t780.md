# bf-4t780 — Add delta population assertions

**Date:** 2026-08-05
**Target:** `governor::window_delta_tests::test_consecutive_snapshots_governor_cycle`
(`src/governor.rs`), the test written under [bf-5pl4o](../notes/bf-5pl4o.md).

## What the test already asserted

- `p5h_delta`/`p7d_delta`/`p7ds_delta` are `None` on a fresh state and `Some(_)`
  after the two snapshots are differenced.
- Each computed delta equals a manual `current - previous` calculation.
- `last_fleet_aggregate.window_pct_deltas` is zero beforehand and non-zero after.

## What this bead added

1. **Non-zero assertions on the state delta fields themselves.** `is_some()` was
   not enough: the first-poll path writes `Some(0.0)` (see
   `test_first_poll_governor_state_no_panic_default_deltas`), so `Some(_)` is
   satisfied by a delta that never saw a second snapshot. The three fields are now
   asserted `!= 0.0`, with the snapshot pair in the failure message.

2. **Every delta assertion anchored to the snapshot inputs.** The expected deltas
   are now computed once from `snapshot1`/`snapshot2` fields and hoisted above the
   delta block; the fleet-aggregate assertions use them instead of the hardcoded
   `2.5`/`2.0`/`3.0` literals. Checking each window field separately means a
   mis-wired field (e.g. `seven_day` fed from the 7ds delta) fails rather than
   passing on shape alone.

3. **A serialization assertion for the delta structure.** The governor persists
   state to `governor-state.json` between cycles, so a delta that only exists in
   memory is not populated in any useful sense — the next cycle and `cgov status`
   read it back from disk. The test now serializes the state and asserts that
   `p5h_delta`/`p7d_delta`/`p7ds_delta` and
   `last_fleet_aggregate.window_pct_deltas.{five_hour,seven_day,weekly_scoped}`
   are present, numeric, and carry the computed values. This pins the field names
   against a rename or a `#[serde(skip)]`.

## Comment correction

The fleet-aggregate section claimed the direct assignment "simulates what
`run_governor_cycle` does when it stores fleet aggregate deltas". It does not:
production annotates the interval's `f` row with the computed deltas
(`db::annotate_window_pct_deltas`, called from `src/governor.rs:4858`) and then
reads `last_fleet_aggregate.window_pct_deltas` back out of that row's
`p5h`/`p7d`/`p7ds` columns (`src/governor.rs:4520-4570`). Same values, longer
route — one that needs a database. The comment now says so.

## Mutation checks

restored after each:

| --- | --- |

Note that the first mutation is caught by the new `assert_ne!` before reaching the
existing equality assertions — the non-zero check is not redundant with them for
the first-poll-style failure it targets.
