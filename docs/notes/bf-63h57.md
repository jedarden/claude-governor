# needle 0.2.16 does NOT fix the worker stderr span leak — governor stays observe-only

**Bead:** bf-63h57
**Date:** 2026-08-06
**Host:** `hetzner-ex44`
**Status:** Resolved — definitive **NO** on 0.2.16; the fix exists but is untagged upstream; governor
left in observe-only, and a governor-side disk guard added so a worker logging bug cannot fill the host.

## Answer to the question the bead asked

**No. needle 0.2.16 does not fix the span leak.** Evidence is git ancestry plus the guard ordering
in the tagged tree, not changelog wording.

| Fact | Value |
| --- | --- |
| Fix commit | `c2d83c3` — *fix(worker): stop holding a span guard across the claim await (bf-3uj6i)* |
| Fix commit date | 2026-08-05 16:32 -0400 |
| `v0.2.16` tag date | 2026-08-02 12:54 -0400 (`8ba4afd`) |
| `git merge-base --is-ancestor c2d83c3 v0.2.16` | **NO** |
| `git tag --contains c2d83c3` | *(empty — no tag contains it)* |

The fix landed three days **after** v0.2.16 was tagged and has never been tagged since. It sits on
`main` only, which `Cargo.toml` calls **0.2.17** — but **there is no `v0.2.17` tag**.

### The defect, at file and line, inside `v0.2.16` itself

Read from `git show v0.2.16:src/worker/mod.rs`:

- **line 1552** — `let _claim_enter = claim_span.enter();` holds an RAII guard on the thread-local
  span stack.
- **line 1608** — `self.bead_lifecycle_span = Some(lifecycle_span.entered());` pushes `bead.lifecycle`
  **on top** while `_claim_enter` is still alive.
- **line 1610** — the comment asserts *"The claim_span (`_claim_enter`) is dropped here"*. It is not.
  It is a `let` binding in the enclosing scope, so it drops at end of scope — **after** `bead.lifecycle`
  was pushed above it.

That is a non-LIFO exit of a stack that requires LIFO order, so neither span is ever popped. One
`bead.claim` plus one `bead.lifecycle` leak **per successful claim**. The fmt layer re-serializes the
whole stack on every event, so line length grows with claim count and output grows quadratically.

The 0.2.17 tree replaces the guard with `.instrument(claim_span.clone())` on the `claim_one` future,
so the span is scoped to the future rather than held across the await, and `bead.lifecycle` becomes
the only entered guard — LIFO-clean.

## Corrections to the bead's premises

Three statements in the bead description were no longer (or never) true. They matter, so they are
recorded rather than quietly worked around.

**1. The deployed binary is 0.2.16, not 0.2.15.** `~/.needle/bin/needle-stable` is dated
2026-08-02 18:21 and reports `needle 0.2.16`. Also, `~/.local/bin/needle` is no longer a symlink —
it is now a regular file, a byte-identical copy (12,836,096 bytes). The conclusion is unchanged:
0.2.16 predates the fix, so the deployed binary is vulnerable either way.

**2. The governor was not stopped — it is running.** `claude-governor.service` is `active` and
`enabled`, restarted 2026-08-06 20:07 under bf-hjage, with `--dry-run` **hardcoded into `ExecStart`**.

**3. The governor does not own the `2>>` redirect.** This is the load-bearing correction, because
deliverable 4 was written on top of it. The configured launch command is plain, with no redirect:

```yaml
launch_cmd: "needle run --agent claude-code-glm-5 --workspace {workspace} --session-prefix needle-cgov"
```

**needle** builds the redirect, in `src/cli/mod.rs:1141-1153`: it composes
`~/.needle/logs/<session>.stderr.log` and appends `2>> <path>` to the inner tmux command itself. The
governor never sees that path and cannot predict it — needle picks the phonetic session suffix at
launch. Rotating it from the governor would mean a second writer racing needle's own over one file,
which is worse than the problem. 0.2.17 fixes this at the layer that owns it (`src/log_writer.rs`,
`SizeCappedWriter`, 2 GiB/worker) and routes tracing to `<prefix>.log`, leaving `.stderr.log` for
panics only.

## Why the disk is not currently at risk

The governor is in `--dry-run`, and `scale_up` returns before launching anything in that mode
(`src/worker.rs`), so **the governor is spawning no workers at all**. The recurrence path from the
2026-08-05 incident is closed. Because `--dry-run` is baked into `ExecStart` rather than passed at
runtime, a reboot restores observe-only too — so the bead's `systemctl --user disable` suggestion is
**not needed**, and disabling would cost the fresh `cgov status`/`forecast` data the dry-run daemon
still produces. The unit is deliberately left `enabled`.

Sixteen needle workers *are* running (`needle-claude-code-glm-4_7-alpha` … `-papa`), but the prefix
shows they are **not** governor-spawned — the governor's configured prefix is `needle-cgov-*`. They
run the vulnerable 0.2.16 and were measured directly:

- `alpha` stderr: 8.5 MB over ~13.7 h ≈ 0.6 MB/hr — not the incident's ~159 GB/hr.
- Max **per-line** span repetition across the whole file: `bead.claim` ×2, `bead.lifecycle` ×1.
  The incident reached 2,488 deep and 629,829-byte lines.

The leak accrues per *successful* claim, and these workers mostly race-lose, so they barely express
it. **This is latent, not absent.** A worker dropped into a fast claim loop on 0.2.16 still explodes,
which is exactly what happened to the two governor-spawned workers on 2026-08-05.

## Governor-side hardening that was actually shipped

Since the governor cannot bound a file it does not own, the bound was put where the governor's real
authority is: **the decision to add another writer.** `scale_up` previously launched workers with no
regard for free disk — the only disk check in the codebase was in `doctor`, a manual diagnostic that
runs nowhere near the scaling loop.

`src/worker.rs` now:

- `disk_use_percent()` reads capacity via `df -P` (POSIX single-line output; plain `df` wraps long
  device names and shifts every column).
- `scale_up_blocked_by_disk()` is a pure predicate over `Option<u8>`, so the threshold is testable
  without filling a real disk.
- `scale_up` refuses to launch at **≥90%** used on the filesystem holding `heartbeat_dir` (under
  `~/.needle`, the same filesystem as the `.stderr.log` files a leaking worker grows).

Two deliberate choices:

- **Fails open on an unreadable `df`.** Unknown is not the same as full; blocking there would wedge
  scaling permanently on any host where df output drifts. Some pseudo-filesystems report capacity as
  `-` and land in this path — procfs, which is why the guard is not tested through `/proc`.
- **Checked before the `dry_run` branch**, so observe-only reports the refusal too. A dry run
  claiming it "would launch" workers the real path would refuse is a misleading forecast.

Tests: 5 added (2 on the df parse, 3 on the threshold). `cargo test --lib` 760 passed / 0 failed;
`worker.rs` clean under `cargo fmt --check` and `cargo clippy`.

## What is still open, and what would close it

Blocked on NEEDLE **bf-3uj6i** shipping a tagged release. Deliverable 2 (upgrade + un-dry-run +
confirm flat stderr) was **not** done, for two reasons:

1. **The fix is untagged.** Deploying a build off `main` would recreate precisely the situation this
   bead opens by complaining about — an untagged binary of uncertain provenance in `needle-stable`.
   It would also swap the binary under the 16 live workers, a fleet outside this bead's scope.
2. **Un-dry-running is independently gated.** Per `docs/notes/bf-hjage.md`, `--dry-run` stays until
   the `launch_cmd` workspace and `session_pattern`/live-fleet mismatch are resolved. Those are
   unrelated to needle and still open, so the governor could not take Act mode even with a fixed needle.

To close: tag needle 0.2.17 (or later) containing `c2d83c3`, repoint `~/.needle/bin/needle-stable`
(and the now-un-symlinked `~/.local/bin/needle`) at it, then resolve bf-hjage's two conditions before
removing `--dry-run`. Verification once workers are governor-spawned: max per-line `bead.claim`
repetition must stay at 1–2 rather than climbing with uptime — line length, not file size, is the
early signal.
